# Feature Specification: 订单创建与支付

**Feature Branch**: `未创建（未启用 Git 扩展）`

**Created**: 2026-09-25

**Status**: Draft

**Input**: User description: "用户确认已锁定的座位与金额后创建订单、完成支付并获得可查看的电影票。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 确认订单并创建待支付订单 (Priority: P1)

已登录用户在有效座位锁定期内核对电影、影院、场次、座位、票价和总额，确认后创建唯一的待支付订单。

**Why this priority**: 订单是座位锁定与支付之间的权威交易记录，必须先保证内容和金额正确。

**Independent Test**: 使用有效锁定创建订单，核对订单项目、金额和到期时间；重复确认只返回同一订单。

**Acceptance Scenarios**:

1. **Given** 座位锁定仍有效且价格未变化，**When** 用户确认订单，**Then** 系统展示完整明细并创建唯一待支付订单。
2. **Given** 锁定已过期、被释放或不属于当前用户，**When** 用户提交订单，**Then** 系统拒绝创建并引导重新选座。
3. **Given** 最新应付金额与页面展示不同，**When** 创建订单，**Then** 系统阻止继续、展示差异并要求用户重新确认。
4. **Given** 用户重复提交同一次确认，**When** 系统处理，**Then** 不创建重复订单或重复占用。

---

### User Story 2 - 安全完成支付 (Priority: P1)

用户为待支付订单选择可用支付方式，在明确同意最终金额后发起支付，并只根据权威支付结果得到成功、失败、取消或处理中状态。

**Why this priority**: 支付直接涉及资金和座位出售，错误成功提示或重复扣款不可接受。

**Independent Test**: 分别模拟支付成功、失败、取消、超时后成功和重复回调，验证订单与座位只发生一次正确状态变化。

**Acceptance Scenarios**:

1. **Given** 订单仍可支付，**When** 权威支付结果确认成功，**Then** 订单变为已支付、座位变为已售并生成电影票。
2. **Given** 支付失败或用户取消，**When** 结果确认，**Then** 订单保持未支付或进入失败/取消状态，不显示购票成功。
3. **Given** 支付结果暂时未知，**When** 用户返回应用或刷新，**Then** 系统显示处理中并主动查询最终状态，不允许盲目重复支付。
4. **Given** 相同支付请求或结果被重复提交，**When** 系统处理，**Then** 最多记录一次有效支付和一次订单成功转换。

---

### User Story 3 - 查看订单与电影票 (Priority: P2)

用户可以查看自己的订单列表和详情；成功支付的订单提供电影票信息，其他账号不能访问。

**Why this priority**: 用户需要在观影前找回购票凭证并确认场次、座位和订单状态。

**Independent Test**: 账号 A 创建成功订单后可以查看票据，账号 B 和游客均无法访问该订单。

**Acceptance Scenarios**:

1. **Given** 用户具有已支付订单，**When** 查看订单详情，**Then** 显示订单号、电影、影院、场次、影厅、座位、金额、支付时间和可验票凭证。
2. **Given** 用户具有待支付、失败或取消订单，**When** 查看详情，**Then** 显示准确状态和允许的后续操作，不展示有效电影票。
3. **Given** 用户尝试访问其他账号的订单，**When** 系统校验身份，**Then** 拒绝访问且不泄露订单是否存在。

---

### User Story 4 - 处理订单超时和恢复 (Priority: P3)

订单或支付流程中断时，用户重新进入应用能够看到权威状态；待支付超时会释放未出售座位，已成功支付的订单不会被错误取消。

**Why this priority**: 移动网络和外部支付可能中断，恢复逻辑决定是否出现重复支付、幽灵订单或座位长期占用。

**Independent Test**: 在支付前、支付处理中和支付成功回调前分别中断应用，重启后订单均恢复为服务端权威状态。

**Acceptance Scenarios**:

1. **Given** 待支付订单超过座位锁定截止时间且没有成功支付，**When** 超时处理，**Then** 订单变为已过期并释放座位。
2. **Given** 客户端超时但支付随后成功，**When** 系统收到权威成功结果，**Then** 不重复扣款，并按交易规则完成或进入人工处理状态，不静默丢失资金记录。
3. **Given** 应用在支付中被关闭，**When** 用户重新打开订单，**Then** 系统查询并显示最终或仍处理中的权威状态。

### Edge Cases

- 支付按钮被连续点击或网络自动重试时，不得创建重复支付或重复订单。
- 支付成功通知与用户主动查询同时到达时，订单状态转换必须只发生一次。
- 支付成功但票据生成暂时失败时，订单保持已支付并可重试生成票据，不得要求再次付款。
- 订单金额必须使用统一货币和最小货币单位计算，避免浮点舍入差异。
- 场次在付款前取消时必须阻止支付并明确后续处理，不得售出无效场次。
- 会话在确认或支付期间失效时，系统要求重新登录并重新校验订单归属和状态。
- 支付服务不可用时，用户可以安全返回订单详情，状态保持可恢复。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 只有有效登录用户才能创建、支付或查看其私有订单。
- **FR-002**: 创建订单 MUST 要求有效且属于当前用户的座位锁定。
- **FR-003**: 订单确认 MUST 展示电影、影院、影厅、场次、座位、单价、费用明细、货币和最终总额。
- **FR-004**: 最终金额 MUST 由服务端根据当前规则重新计算；与客户端展示不一致时 MUST 阻止确认并要求用户重新核对。
- **FR-005**: 同一座位锁定最多对应一个有效订单，重复创建请求 MUST 返回同一订单或明确的已处理结果。
- **FR-006**: 新订单 MUST 具有稳定订单号、创建时间、支付截止时间和 `待支付` 初始状态。
- **FR-007**: 订单状态 MUST 至少区分待支付、支付处理中、已支付、支付失败、已取消和已过期。
- **FR-008**: 发起支付前 MUST 再次校验订单归属、订单状态、场次状态、座位锁定和最终金额。
- **FR-009**: 系统 MUST 只根据权威支付确认把订单标记为已支付；客户端返回页面或按钮状态不得作为成功依据。
- **FR-010**: 支付发起与结果处理 MUST 幂等，相同请求或重复结果不得造成重复扣款、重复订单或重复票据。
- **FR-011**: 支付结果未知时 MUST 显示处理中并允许安全查询，禁止直接显示成功或引导用户盲目重复支付。
- **FR-012**: 支付失败或取消 MUST 显示明确状态和可用操作；在锁定仍有效时允许安全重试。
- **FR-013**: 待支付订单超过座位锁定截止时间 MUST 变为已过期并释放未购买座位。
- **FR-014**: 支付成功 MUST 原子地把订单变为已支付、座位变为已售并生成或排队生成唯一电影票。
- **FR-015**: 已支付订单 MUST 提供可查看的票据信息；未支付订单不得提供有效验票凭证。
- **FR-016**: 用户 MUST 能查看自己的订单列表和详情，且任何账号不得访问其他账号的私有订单。
- **FR-017**: 应用重启或支付流程中断后 MUST 从权威来源恢复订单状态。
- **FR-018**: 日志、错误信息和分析数据不得包含完整支付凭据、敏感令牌或不必要的个人信息。
- **FR-019**: 本功能 MUST 记录可追踪但脱敏的订单和支付状态变化，以支持问题调查和幂等判断。
- **FR-020**: 本阶段不包含退款、改签、优惠券、发票和影院现场验票管理。

### Key Entities

- **订单**: 用户对一组锁定座位的购买意图，包含订单号、用户、场次、金额、货币、状态和时间信息。
- **订单项目**: 订单中的电影、影院、场次、影厅和座位价格快照，支付后保持可追溯。
- **支付尝试**: 针对订单的一次支付发起，包含稳定请求标识、金额、状态和权威交易引用。
- **电影票**: 仅由已支付订单产生的观影凭证，关联唯一订单、场次和座位。
- **状态事件**: 订单和支付的脱敏状态变化记录，用于恢复、审计和重复处理判断。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 至少 90% 的测试用户能在 2 分钟内核对订单并完成一次正常支付流程。
- **SC-002**: 在 100 次重复提交、重复通知和并发状态查询测试中，重复扣款、重复订单和重复票据次数均为 0。
- **SC-003**: 所有订单确认测试中的电影、影院、场次、座位和最终金额与权威记录一致率达到 100%。
- **SC-004**: 支付成功、失败、取消、未知和超时五类结果均在 5 秒内显示已知状态或明确的处理中说明。
- **SC-005**: 100% 的已支付订单可恢复电影票；100% 的未支付订单不能生成有效票据。
- **SC-006**: 跨账号订单访问和修改测试的拒绝率达到 100%，且响应不泄露订单详情。
- **SC-007**: 应用在支付流程任意阶段中断后，重新进入订单详情得到错误成功状态或重复支付的次数为 0。

## Assumptions

- 用户认证由 `001-account-authentication` 提供，场次与座位锁定分别由 `002` 和 `003` 功能提供。
- 支付由具备权威成功/失败结果的外部或模拟支付渠道处理，具体渠道选择留到技术计划阶段。
- 订单货币在单笔订单内固定，金额使用最小货币单位表达。
- 支付截止时间不得晚于座位锁定截止时间。
- 本功能不处理真实退款、改签、优惠券、发票和影院现场验票设备。
