# Spring Boot 后端重构成本评估

> 评估日期：2026-09-27；基线为当前 `backend/` 的 Flask + SQLite 实现及 [项目技术总结](./项目技术总结.md)。这里的“重构”指在不牺牲现有业务语义的前提下，用 Java/Spring Boot 重建后端，而不是只把 HTTP 路由翻译成 Controller。

## 结论

值得重构的前提是项目要进入多人协作、长期维护或生产部署阶段，并且团队的主要后端能力在 Java 生态。若目标仍是本地演示、课程项目或单实例服务，当前 Flask 版本已经覆盖了复杂业务，直接重写的收益不足以抵消风险。

以“对 Android API 零破坏、迁移到 PostgreSQL、保留全部业务测试语义”为标准，建议预留 **14–20 人周**：一名熟悉 Spring 事务和测试的工程师约 **3.5–5 个月**；两名后端工程师并行、另有测试支持时约 **8–12 周**。若只是框架替换、继续使用 SQLite 且不做部署/观测增强，可压缩至 **8–12 人周**，但不会解决单实例写锁和生产运维问题。

## 1. 现有资产与重构范围

当前后端不是一个只有几个 CRUD 接口的 Flask 服务。业务代码约 1,876 行（不含测试），分布在 `app.py`、`auth.py`、`showtimes.py`、`seats.py`、`orders.py`、`payments.py`、`favorites.py` 与 `recommendations.py`；后端自动化套件目前有 45 项实际运行测试。API 包含约 30 个路由，且 Android 客户端已经依赖其字段、错误码、HTTP 状态码、幂等行为和时间语义。

必须等价迁移的模块包括：

| 模块 | 现有关键行为 | Spring 重构复杂度 |
| --- | --- | --- |
| 认证与会话 | scrypt 密码哈希、token 摘要存储、可撤销 30 天会话、登录限流、退出时释放锁 | 中 |
| 场次查询 | 时区下的本地日期、筛选、距离排序、场次版本校验 | 中 |
| 座位库存 | 1–6 座限制、过期锁、幂等键、座位集合指纹、并发抢座的全有或全无 | 高 |
| 订单与支付 | 权威报价、唯一订单、支付状态机、回调验签/去重、出票、退款回补库存 | 很高 |
| 收藏同步 | 离线操作日志、设备哈希、按 revision 增量拉取、冲突收敛、tombstone | 高 |
| 推荐 | 内容特征、协同过滤、冷启动降级、目录抓取、推荐快照与事件归因 | 高 |
| 旧同步兼容 | `/sync/push`、`/sync/pull` 的资料/评论/评分历史行为 | 中 |

难点不在于把 Python 语法改成 Java，而在于保留上述跨模块不变量。例如，支付成功必须使订单、票券和座位状态一致；退款只能重开该订单的已售座位；重复 webhook 不能重复出票；收藏离线重试不能越权或覆盖其他设备的后续状态。

## 2. 两种目标方案与成本

### 方案 A：兼容型迁移（不建议作为终态）

采用 Spring Boot + JDBC/JdbcTemplate，继续读写 SQLite，仅为团队技术栈统一而迁移。优点是表结构和 SQL 逻辑可较快复用；缺点是 SQLite 的单写者特性仍在，Spring 的并发能力无法使其变成多实例库存数据库。

- 估算：8–12 人周。
- 适用：内网工具、开发环境、短期的 Java 化过渡。
- 主要风险：容易在“代码看似等价”时丢失 `BEGIN IMMEDIATE` 的库存互斥语义；无法获得高可用和水平扩展收益。

### 方案 B：生产化重构（推荐）

采用 Spring Boot、Spring Web、Spring Validation、Spring Security（或自定义 Bearer filter）、JPA/JdbcTemplate、Flyway、PostgreSQL，并用 Testcontainers 运行集成测试。库存/订单等强一致路径保留显式事务与条件更新；推荐、目录同步和过期清理改为受控的调度任务；应用以容器化方式部署并增加健康检查、指标和结构化日志。

- 估算：14–20 人周。
- 适用：准备接入真实支付渠道、多人维护、容器部署或未来多实例扩展。
- 主要收益：可靠迁移、可审计 schema 版本、连接池与并发能力、事务和可观测性更加标准化。

## 4. 推荐的 Java 架构与关键实现

```text
api (Controller + request/response DTO + Validation)
  └── application (用例：Auth、Seat、Order、Payment、Favorite、Recommendation)
       └── domain (状态机、策略、领域规则)
            └── infrastructure
                 ├── persistence (PostgreSQL + Flyway + Repository/JdbcTemplate)
                 ├── external (猫眼目录、支付 Provider)
                 └── security / scheduler / observability
```

1. **以 API 契约优先，而不是以表优先。** 先从现有 Android DTO、`specs/*/contracts` 和 Flask 测试冻结请求、响应、错误码、字段名及状态码。只要这些不变，Android 的 Ktor、Repository 与 ViewModel 原则上无需改动。
2. **库存路径使用短事务。** 在 PostgreSQL 中可用 `SELECT ... FOR UPDATE` 锁定候选座位，或采用 `UPDATE ... WHERE status='AVAILABLE'` 后校验更新行数；必须在同一事务内写 lock、lock items 和座位状态。不要把“先查询可用、再逐条更新”的逻辑放到事务外。
3. **幂等约束下沉到数据库。** 为 `(user_id, idempotency_key)`、`(order_id, idempotency_key)`、`seat_lock_id`、`ticket.order_id`、`payment_event.id`、`client_operation_id` 等建立唯一约束。服务层捕获唯一冲突后返回原结果或可预期业务错误，而不是 500。
4. **状态机集中化。** 把订单、支付尝试、座位锁和票券的允许转换写成显式 domain service；数据库约束用于兜底，Controller 不应直接拼状态更新 SQL。
5. **过期处理同时“读时校验 + 定时补偿”。** 现有实现会在关键读写路径即时清理过期订单/锁。Spring 版应保留这一行为，并增加带租约或数据库互斥的调度任务，不能只依赖定时任务。
6. **推荐优先保证可复现。** 先逐项复刻当前算法版本、候选排除规则和 fallback，再考虑引入向量检索或异步特征计算；否则无法区分“语言迁移差异”和“算法效果变化”。

## 5. 主要风险与控制措施

| 风险 | 可能后果 | 控制措施 |
| --- | --- | --- |
| 库存事务语义被弱化 | 重复锁座、已售座位被重开 | 并发集成测试；数据库行锁/条件更新；所有改库存路径走同一服务 |
| API 微小不兼容 | Android 映射失败、错误提示错误、旧版不可用 | 从 Android 请求录制/契约文件生成回归测试；双服务响应 diff |
| 直接复制 SQLite schema | 索引、时间类型、约束和自增/UUID 行为异常 | 以 Flyway 重建 Postgres schema，逐表导数后做计数与校验和比对 |
| 重写期间双写不一致 | 订单、收藏或支付事件丢失/重复 | 先影子读校验；强一致交易切流采用短暂维护窗口，避免长期无事务双写 |
| 推荐结果变化 | 点击/收藏体验退化，测试失真 | 固定测试目录、固定时间和确定性排序；先通过结果快照回归 |
| “框架重写”顺便扩需求 | 工期失控 | 锁定 API 与业务规则；真实支付、Redis、MQ、后台系统另列 backlog |

## 6. 迁移路线：并行替换，不停机重写

1. **第 0 阶段：冻结行为（约 1 周）**：补齐/整理 OpenAPI 与黑盒契约用例，保留 Flask 的 45 项回归测试作为行为基线；对并发锁座、回调重复、退款、离线收藏冲突建立固定场景数据。
2. **第 1 阶段：搭建 Spring 与只读影子接口（约 2 周）**：先实现健康检查、认证只读、场次、订单查询等，代理或测试环境中对比 Flask/Spring 响应，处理序列化和时区差异。
3. **第 2 阶段：迁移写路径（约 3–5 周）**：先收藏同步，再座位锁、订单、支付、退款。每一块先在隔离环境通过并发和幂等测试；库存与支付切换必须具备停写、导数、校验和回滚步骤。
4. **第 3 阶段：迁移推荐与任务（约 1–2 周）**：导入目录/行为数据，验证同一输入得到相同排序或可接受的等价结果；再启用定时刷新与指标。
5. **第 4 阶段：灰度切流与退役（约 1–2 周）**：由 API 网关/反向代理逐步将流量切至 Spring；观察错误率、库存冲突率、回调滞后、订单终态比例和收藏同步失败率。稳定后将 Flask 保留为短期只读回退，再退役。

生产迁移不建议让 Flask 与 Spring 长期同时承担同一订单写入，因为跨服务双写会破坏库存与支付的原子性。更安全的做法是：完成校验后，在一个短维护窗口内将某个强一致写域整体切到新服务。

## 7. 决策建议

- **继续 Flask**：当前项目以展示、学习或单机局域网部署为目标，开发者对 Python 更熟，且没有真实支付和多实例要求。这是最低风险、最低成本的选择。
- **选择 Spring Boot 重构**：团队以 Java 为主，需要规范化分层、Flyway、PostgreSQL、容器运维和未来扩展。优先做方案 B，不建议仅“把 Flask 换成 Spring、数据库仍用 SQLite”。
- **暂不启动的信号**：现有 API 仍频繁变化、无明确部署目标、没有可投入的 14–20 人周、或无法为库存/支付迁移安排压测和切换窗口。在这些条件下，应先增强当前 Flask 的契约、Docker 化、PostgreSQL 迁移或测试，而不是同时更换语言与数据库。
