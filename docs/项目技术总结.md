# MovieTicketHub 项目技术总结

> 代码盘点日期：2026-09-27。本文以当前仓库实现为准；`backend/app.py` 是 Flask 服务的路由装配、数据库初始化和迁移入口。

## 1. 项目定位与整体架构

这是一个 Android 电影票务应用：客户端从猫眼接口获取影片数据，用户可浏览、搜索和查看影片详情；登录后可收藏、选择城市/影院/场次、锁定座位、创建订单、完成模拟支付、查看电子票并退款。项目并非只有 App 演示界面，还实现了一个以 SQLite 为存储的 Flask 本地服务，用于承载账号、票务库存、订单支付、收藏同步及推荐。

```text
Jetpack Compose UI (MVI / ViewModel / StateFlow)
        │
        ├── 影片数据：Ktor ──> 猫眼公开接口
        └── 业务数据：Ktor + Bearer Token ──> Flask app.py
                                              │
                  auth / showtimes / seats / orders / payments /
                         favorites / recommendations
                                              │
                                           SQLite
        │
Room：账号隔离的收藏本地状态、待同步操作、游标及部分历史本地数据
Android Keystore：AES-GCM 加密保存会话令牌
```

前端按 `presentation`、`domain`、`data` 分层：Compose Screen 负责渲染和事件分发，ViewModel 维护不可变 UI 状态，Repository 屏蔽远端 API 与 Room 的差异，Domain 层定义模型和接口。依赖通过 Koin 注入。后端虽是单进程 Flask，但将路由、认证、场次、库存、订单、支付、收藏与推荐拆到独立模块；`create_app()` 统一初始化 schema、开发种子数据和迁移逻辑。

## 2. 当前已实现功能

### 电影内容与基础体验

- 启动页会恢复会话；失效或未登录则进入游客模式。游客可以浏览影片，但收藏、选座和购票会被登录门控拦截。
- 展示正在热映、即将上映、影片搜索、影片详情、演员与简介；影片内容通过 Ktor 拉取猫眼数据，Coil 负责图片下载和缓存。
- Compose Navigation 采用类型化路由，在影片列表、详情、影院、场次、座位、支付、订单、设置、搜索和收藏页面间传递最小且可序列化的参数。

### 账号与会话

- 支持注册、登录、`/auth/me` 校验和退出登录；账号以邮箱规范化后唯一。
- 后端用 Werkzeug `scrypt` 保存口令哈希，原始 session token 只在创建时返回，数据库只保存 SHA-256 摘要。
- session 可撤销、有 30 天有效期；连续 5 次登录失败会触发按邮箱和来源组合计算的 15 分钟限流。
- Android 端将 token 以 Android Keystore 管理的 AES/GCM 密钥加密后写入 SharedPreferences；退出网络失败时转入“待撤销”区，下一次启动会补偿撤销请求。

### 收藏与跨端同步

- 收藏列表支持添加/取消、离线优先显示和账号隔离。Room 保存“服务端确认状态、用户期望状态、同步状态、服务端 revision”和本地操作日志。
- 每个操作携带 UUID、设备 ID、单账号递增序号；同步接口会返回操作结果和 revision 增量，客户端据此确认、拒绝或覆盖本地状态。
- `FavoriteSyncCoordinator` 用 `Mutex` 串行化同进程同步，并对可重试网络错误进行 3 次指数退避（100/200 ms）。
- 仓库还保留了旧的 `/sync/push`、`/sync/pull` 全量同步通道，用于历史的资料、评分、评论、点赞和本地订单数据；收藏已明确改走新的权威增量同步通道，二者不能混用。

### 选影院、场次与座位库存

- 后端提供电影可售日期、按城市/日期/行政区/时间段/价格/排序/经纬度查询影院和场次，以及基于版本号的场次复核。
- 场次包含时区和销售状态；筛选按影院本地日期进行，距离排序使用 Haversine 公式，避免仅以服务端 UTC 日期或平面坐标造成的偏差。
- 座位图含过道/空位、价格分区和逐座库存状态。客户端每 5 秒拉取快照，并区分“我锁定”“他人锁定”“已售”等状态。
- 用户一次可选 1–6 个座位。锁座成功后依据服务端 `serverTime` 和 `expiresAt` 倒计时；使用 `elapsedRealtime()` 计时，减少设备改时钟带来的显示漂移，并在前台恢复时重新向服务端确认。

### 下单、支付、出票与退款

- 锁座后先获取服务端权威报价，客户端接受 `quoteVersion` 后才能创建待支付订单，金额使用 `amountMinor`（分）而非浮点数。
- 支持支付宝、微信的模拟支付方式：创建支付尝试、确认支付、接收模拟 provider webhook、生成电子票、订单列表/详情、票券列表与退款。
- 支付成功才会将锁定座位原子转换为 `SOLD`，同时写入订单状态事件与票券；订单超时会取消支付尝试并释放未售座位。退款会把已售座位恢复为可售，并将订单、票券标识为退款。
- 客户端在余额不足、支付失败或离开未支付页面时主动释放锁；最终库存判断仍由服务端完成。

### 推荐与行为闭环

- 服务端维护电影目录，可在启动时填充种子数据，也可拉取与客户端相同的猫眼热映列表，使推荐返回的电影 ID 可直接打开已有详情页。
- 对登录用户，推荐排除已收藏和已购影片，综合内容偏好（类型/主题）、热度、新鲜度以及多用户隐式反馈的 item-item 协同过滤；冷启动、无候选或外部目录不可用时降级到热度/热映结果。
- 每一次推荐均记录 `recommendation_runs` 和带“原因文本/匹配特征”的候选项；曝光、点击、收藏、购买事件以事件 ID 去重写入指标表，后续可用于优化排序与评估。

## 4. 技术难点与实现思路

### 4.1 高并发锁座：从“展示状态”变成“库存事务”

难点是多个用户同时点击同一座位时，不能因为客户端快照过期而重复售卖。实现将最终裁决放在服务端：`create_lock()` 先清理过期锁，再以 SQLite `BEGIN IMMEDIATE` 获取写锁，仅对仍为 `AVAILABLE` 的目标座位执行带状态条件的更新。任一座位不满足条件就返回 `SEAT_CONFLICT` 和最新库存版本；全部更新成功后才建立 lock 与 lock items。锁座还同时使用请求幂等键和“同用户、同场次、同座位集合指纹”去重，兼顾网络重试和客户端误生成新 key 的情况。

状态流转为：

```text
AVAILABLE --锁座(15 分钟)--> LOCKED --支付成功--> SOLD
    ^             │               │
    └──释放/超时──┘               └──退款后回到 AVAILABLE
```

客户端轮询只是改善可见性，倒计时只是体验层提示；服务端过期检查和条件更新才是正确性的根基。

### 4.2 订单与支付：防重复扣款、防陈旧报价、防迟到回调

订单从锁座快照生成，报价版本由服务端控制，客户端传回已接受版本。座位锁、订单和支付尝试分别有唯一约束/幂等键：同一 lock 只会生成一个订单，同一订单和支付幂等键只会生成一个支付尝试。支付模块以状态机处理 `PENDING_PAYMENT → PAYMENT_PROCESSING → PAID/PAYMENT_FAILED/CANCELLED/EXPIRED`；终态优先于重复、延迟或乱序的 provider 通知。成功分支中先把整组 `LOCKED` 座位转换为 `SOLD`，再更新订单和出票，避免“已支付但座位未售出”或清理任务误释放已售座位。

金额在所有接口和表中均为整数分，避免 `Double` 累积误差。状态事件表保留来源、原因、关联 ID 和时间，既便于排障，也为未来接入真实支付网关和审计提供骨架。

### 4.3 离线优先收藏：本地意图与服务端事实分离

收藏不能简单地“本地布尔值覆盖远端布尔值”，否则多设备操作和断网重试会丢失意图。项目把每次点击记录为独立操作，本地先更新 `desiredState` 以保证 UI 即时响应，再由服务端为操作分配全局 revision。下次同步使用 cursor 获取所有漏掉的增量，服务端操作结果决定本地操作是 `CONFIRMED`、`REJECTED` 还是 `FAILED`。这一设计让重试可安全执行、设备间变化可追赶，且收藏表以 `accountId` 为键实现隔离。

### 4.4 会话安全与“可用性—安全性”平衡

移动端不会明文保存 token，后端也不会保存原 token；即使数据库或偏好文件泄露，直接复用的风险被显著降低。另一方面，退出登录不能因临时断网而遗留长期有效 session，因此客户端把 token 移到加密的待撤销区并在后续恢复时重试。API 侧统一使用 Bearer session 解析和用户 ID 过滤，座位、订单、票券、收藏和同步均不会由客户端传入任意用户 ID 进行越权查询。

### 4.5 个性化推荐：可解释、可降级、可度量

推荐不是仅在 App 端随机打分。服务端以收藏、购票和有效行为事件构成隐式反馈集合，并结合内容特征和协同信号；每项结果保存分数、原因类型、原因文案、匹配特征以及算法/目录版本。这样的“结果快照 + 事件回传”结构能回答“当时为什么推荐”“用户是否点击”，也使目录抓取失败、无登录、偏好不足时可明确降级而不让界面空白。

## 5. 工程质量与可运行边界

- 后端测试覆盖认证、场次筛选、锁座并发、订单、支付安全、收藏同步、推荐隔离等主题；Android 侧覆盖 ViewModel、Repository、Mapper、Room 迁移、登录和收藏 UI 等。当前后端 `unittest` 套件实际运行 45 项测试；Android 源码中有 38 个 `@Test` 标记。
- Debug 包将后端地址指向 Android 模拟器的 `http://10.0.2.2:5000`；Release 默认地址为占位域名，实际发布必须替换为 HTTPS 服务并置于反向代理之后。
- 这是适合本地开发、课程/作品展示的单体实现。SQLite 的 `BEGIN IMMEDIATE` 能保证单实例内锁座正确性；扩展到多进程/多实例生产部署时，应把库存事务迁移至 PostgreSQL/MySQL 等共享数据库，并补充队列、分布式幂等、真实支付签名校验、监控告警和密钥管理。
- 猫眼目录同步是外部网络依赖，服务端已实现失败回退；生产环境还应加入缓存、定时任务、限流和对上游接口变更的契约监控。
- 旧全量 `/sync` 与新收藏增量同步并存是历史兼容安排。后续重构应明确旧通道中订单/评论等数据的权威来源，逐步收敛协议，避免两套同步模型长期维护。

## 6. 结论

项目的核心价值在于把一个 Compose 电影浏览 Demo 扩展成了具备服务端权威性的一条票务业务链路：客户端负责交互、缓存和恢复，服务端负责认证、库存、价格、订单、支付状态和推荐结果的最终判定。尤其是锁座事务、支付状态机、操作日志式收藏同步、加密可撤销会话和可解释推荐，体现了从“页面功能”走向“可验证业务一致性”的设计思路。
